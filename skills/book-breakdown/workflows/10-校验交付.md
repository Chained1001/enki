# 10 校验交付

## 目的

完成PRD 产品流程节的阶段 7：脚本校验、引句回源核验、错误修复循环、交付汇总。

## 输入

| 字段 | 必需 | 说明 |
|---|---|---|
| 产物目录 | 是 | 09 已完成 |
| 原文目录 | 否 | 默认取产物目录下的 `原文/章节/`（prepare 已生成）；缺失时核验只报脚本结果 |

## 视野

**远景（核验例外）**｜读原文：**禁止人工通读**；核验由 `verify-quotes.mjs` 脚本做，`not-found` 条目交子代理按条目核

核验要比对全书的引句与原文，人工读不可能读完；脚本逐条查表。子代理只拿到 `not-found` 条目清单，不是整本书。

三档含义见 `../SKILL.md` 的「视野分级」节；与上下阶段的衔接见 PRD 产品流程节的「视野分级」横向规则。


## 步骤

1. 运行交付校验：`node ../scripts/validate-output.mjs <产物目录>`。
2. 错误级问题：按失败清单逐条修复对应文件后重跑校验；只动清单指向的文件，不碰其他产物。

   **每轮修完都要登记轮次，否则「三轮上限」不存在**：

   ```
   node ../scripts/progress.mjs <产物目录> --repair-round 1:E_SOURCE 出处补齐
   ```

   为什么必须落盘：停止条件写的是「同一错误修复三轮仍未通过」，可轮次此前只活在对话里——中断重跑就从头数，于是这个上限可以被无限重置，等于没有。登记后 `progress` 会打印已用轮次，超过 3 轮就按停止条件处理。

   登记的是「第几轮 + 这一轮改了什么」而不是纯计数：重跑时要靠它知道上一轮试过哪些改法，才不会把同一个改法再试一遍。同一轮重复登记会覆盖而不是追加（重跑同一轮很常见，追加会让轮次虚高、三轮上限提前触发）。
3. 运行引句回源核验：`node ../scripts/verify-quotes.mjs <产物目录>`；需要完整清单时加 `--json --max-findings <不小于 not-found 计数的 N>`，默认只列前 50 条。
4. 按核验结果分流：`pass` 与 `wrong-chapter` 由脚本定论，不交子代理；`wrong-chapter` 直接按脚本给的章号改该条出处。
5. 只把 `not-found` 条目交子代理，**分两段做**：

   **先让脚本定位，别让子代理自己检索。**把 `not-found` 条目写成 `[{"编号":"n1","引句":"…"}]`，跑

   ```
   node ../scripts/quote-finder.mjs <产物目录> --grep-all <引句.json>
   ```

   它一次读完全书、建 4-gram 倒排，然后给每条引句打印候选章号与候选句（无命中也明说）。子代理只判「命中的那句是不是同一意思」，不做检索。

   为什么要拆开：子代理此前是**逐条自己检索**，单条上限 8 轮全书搜索、3 分钟。绍宋实测 `not-found` 120 条 ≈ 6 小时，而其中大部分时间花在「这本书里到底有没有这句」——那是确定性检索，不是语义判断。脚本一遍扫完，子代理的工作量从「找 + 判」降到「判」。

   **再按每批 ≤20 条交子代理**：按 `../agents/出处核验.md` 调用，传入产物目录、本批 `not-found` 条目清单（含脚本定位结果）、原文目录 `原文/`；`pass` 与 `wrong-chapter` 条目不进清单。

   为什么分批：120 条一次给，子代理在第 90 条崩掉时前 89 条的裁决全丢——而它的返回值是唯一载体。20 条一批共 6 批，崩一批只重做那一批。
6. **每批裁决当场追加写进「工作/增量/裁决.json」，不要等全部做完再汇总**：

   - 用 write／edit 把本批裁决**追加**到该文件末尾（JSON 数组，每条含 `编号`、`裁决`、`章号`、`依据句`、`说明`）。追加而不是覆盖，中断重跑时只补没做过的那几批。
   - 写完立刻登记本轮进度：`node ../scripts/progress.mjs <产物目录> --repair-round <轮次>:出处核验第<k>批`（轮次从 1 起，同一批重跑用同一个轮次号会覆盖而不是追加）。

   子代理**仍然只读**：落盘是调用方的事，它的工具白名单里没有写文件（见 `../agents/出处核验.md` 的只读约定，别为了省事放开）。这条不是为了省事——子代理一旦能写产物，「裁决来自哪一条」就没法复核了。

   为什么必须落盘：裁决此前只存在于子代理的返回值里。120 条跑到第 90 条崩掉，前面 89 条全丢，重跑从第 1 条再来。

7. 检查子代理返回的每个必需字段；缺任一字段或该条判定为「未裁决」，不采信该条，记入存疑清单。
7. 按裁决处置：转述用其给出的原文整句替换引句，拼接按片段分别标章号或改写为单章引句，编造删除该条结论并记入存疑清单；未裁决的原结论保留不动，标「存疑」并记入存疑清单，交人核对，不按编造删除。
8. 重跑引用核验与交付校验：`validate-output.mjs` 须退出码 0；`verify-quotes.mjs` 重跑后只剩未裁决条目对应的 `not-found` 时即收口，不追退出码 0。转述与拼接处置过的条目须转为 `pass` 或 `wrong-chapter` 并当场改掉章号。
9. 警告级问题：逐条记入交付报告，不阻断、不强行消除。
10. 成本核对（M-06）：`node ../scripts/cost.mjs <产物目录> --report`。
    报告给出各阶段输入/输出与占比，并用产物算出的下界交叉核对。出现 `W_COST_UNDER`（上报值低于「读一遍全书」的下界）说明有阶段漏记，回头补；`W_COST_STAGE_MISSING` 列出没有记录的阶段。若全程完全没记录，`--check` 退出 1——按 M-06「无计量即不通过」处理，不要跳过。
11. 全部通过后输出交付汇总：产物目录树、文件数统计（按产物类别）、引句核验结论（三档计数＋裁决合计＋未裁决条数）、成本小结（合计 tokens 与阶段占比）、警告清单、存疑清单（08 遗留与本轮裁决新增）。
12. 标记阶段 7 done：`node ../scripts/progress.mjs <产物目录> --stage 7:done`。
13. 中途用户要查进度：以 `--mode progress` 跑校验或用 progress 只读输出，不打断。

## 产出

- 校验通过的完整产物目录。
- 引句核验结论一段：`pass`、`wrong-chapter`、`not-found` 三档计数，裁决合计（转述、拼接、编造各几条），以及未裁决条数。
- 交付汇总一段（目录树＋文件数＋警告与存疑清单）。

## 停止条件

- 同一错误修复三轮仍未通过：停止，输出当前失败清单与已尝试的修复，等待用户裁决。
- 校验器本身报错（如 E_MANIFEST）：说明产物目录不完整，回到 05 对账续跑。
- `not-found` 裁决为「编造」的条目：删除该结论后该段无条目时写一行「无」，不删段名、不留空段；该条进存疑清单并在交付报告写明删除理由。校验器只查段名存在（E_SECTION），不查段内是否为空，因此不产生新错误码。
- 子代理返回缺字段或整批「未裁决」：不采信该批结果，记入存疑清单后继续交付，不用脚本结果冒充裁决。
- `not-found` 经子代理判定为「未裁决」（多为 8 轮零命中）：原结论保留并标「存疑」，不按编造删除；该条计入交付报告的未裁决条数，交人核对。这类条目的 `not-found` 计数不归零，`verify-quotes.mjs` 会持续退出 1——按步骤 8 收口，不以退出码 0 为交付前提。
